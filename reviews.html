The 125 ms lean status sweep (GET /api/v1/schedule with a fields projection, ~2.4 KB) is the fastest signal that a review was called — MLB flips status.statusCode instantly, while play text lands at resolution. Play-by-play uses the lean /playByPlay endpoint with a tight projection (not the 1–2 MB full feed), staggered per game, with a concurrency governor (6), request deduplication, 1-hour caching of static registries, and full HTTP 429 + Retry-After handling. Polling pauses when the tab is hidden. Only public, keyless StatsAPI endpoints are used.

Unofficial fan project. Live data via the public MLB StatsAPI (statsapi.mlb.com) — manager challenges, crew chief/umpire reviews and boundary calls come from the live game feed's reviewDetails, ABS pitch challenges from absChallenges / pitch-level review events, and official-scorer pending rulings (hit vs. error vs. fielder's choice undecided) come from the API's own event-type registry — os_ruling_pending_primary / os_ruling_pending_prior, description "Official Scorer Ruling Pending" (GET /api/v1/eventTypes). A pending ruling decides how the play is charged and never removes a run from the score. Challenges-remaining counters are the official per-team values read directly from the StatsAPI (review.away/home.used/remaining for manager challenges; gameData.absChallenges.away/home.usedSuccessful/usedFailed/remaining for ABS) — never derived by counting feed events, and never zero-filled when a counter is absent (e.g. pre-ABS seasons). A used-counter that moves backwards between polls is flagged as an irregularity on the affected rows instead of being corrected or hidden. The score tracker separates the observed call-on-field score, conditional possibilities, and an attributable official score after resolution when exposed. Possibilities use only runs tied to the reviewed event and are not predictions of the ruling or runner placement. A review is flagged Runs at Risk only when the official payload credits one or more scoring movements to the very event under review, so an overturn could take those runs back off the scoreboard. Unrelated runs from earlier in the same plate appearance (a steal of home, a wild pitch) are excluded, and whether replay actually removes a run is never predicted. Official scoring changes (a hit reclassified as an error or vice versa, a single changed to a double or back, a base hit changed to a fielder's choice + error, an out changed to a hit, and so on) are tracked in the ✏️ Scoring Changes tab, in the All feed, and in the separate ✏️ Official Scoring Log section below the feed by snapshotting every completed play's official classification (result.eventType / result.isOut / count.outs / error movements in runners[]) on every poll and diffing it against the previous polls — the StatsAPI payload carries no scoring-change marker, so the initial call and the final ruling are known only from consecutive observations. Each row shows the observed initial call and the final ruling, the official score after the play, and an attribution note. Changes that coincide with a replay review stay on that review's row; everything else is attributed as an official scoring change (per MLB's own log, changes are made by the Official Scorer, the Elias Sports Bureau, or after a player/club review — mlb.com/official-information/scoring-changes). A change can only be tracked when its initial call was observed before the change landed; finals are re-scanned for 30 minutes after they end (at most every 30 seconds) to catch rulings published after the game. Payload edits without a reclassification (description / RBI / score only) and plays that vanish from the payload are flagged as irregularities for review, never corrected or hidden. Live game state (score, count, outs, batter, pitcher, pitch count, bases, inning — timestamped down to the second) is captured for every game on the slate on every poll and shown in the 📡 Live Game State section; every challenge, review, pending ruling and scoring change keeps its exact official wording before and after. The alert sound is a single pleasant 3-second raindrop chime (synthesized locally, no audio files) that fires for every event in the alert feed; toggle it on/off or press 🔔 Test Sound to verify it. The scoring log is a separate persistent system (own localStorage keys + own /api/scoring-log endpoints) so it survives refreshes without ever disrupting the alert system. Every tracked entry is also logged to this browser (one log per date, newest seven dates kept, 500 most-recent rows) so a refresh or a later visit restores the feed rows, the scoring baselines and the flagged irregularities before the first scan runs; the log holds only observed payload data, and anything malformed in it is dropped with a console warning rather than guessed.
